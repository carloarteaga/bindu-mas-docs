# Bindu Node Installation Guide

> [!NOTE]
> **HUMAN OPERATOR / SYSADMIN REFERENCE ONLY**
> This document is intended for human system administrators and platform infrastructure operators. Autonomous AI Agents building Multi-Agent Systems (MAS) should NOT use this document and must strictly follow the Whitelisted Curriculum defined in [AGENTS.md](./AGENTS.md).

This guide explains how to install a Bindu **node** using `bindu-install-node`.
It is written for operators who want a reliable, repeatable install without digging into internals.

## 1) Overview

A **Bindu root** is the hub of the mesh.
A **Bindu node** is a connected participant that runs workloads and communicates with the root.

High‑level flow:

1. Root is installed and running.
2. You prepare node network reachability to root.
3. You run `bindu-install-node` on the node.
4. The node connects securely to root using **bootstrap hints** and the **signing_url** embedded in the bundle.

## 2) Prerequisites

Before installing a node, ensure:

- **Root is installed and running.**
- **The node already exists in mesh and mesh is applied.**
  - Use `bindu-studio mesh add` to create it.
  - Use `bindu-studio mesh apply` to persist it.
  - Verify with `bindu-studio mesh tree --all` that `node_id` exists before running `bindu-install-node`.
  - See **Bindu Studio Mesh User Manual** for the authoritative mesh workflow.
- **Node OS is supported:** Linux only.
- **Root OS is supported:** Linux only.
- **Required ports are open** between the node and root:
  - Mesh MQTT port (from your root config)
  - Root HTTPS REST port used for signing (from `bootstrap.json` → `signing_url`)
- **Name resolution is optional for bootstrap.**
  The bundle provides concrete connection hints for first contact (IP-first).
  `node_id` is a logical identity and does not need DNS resolution.

### Linux time sync (required)

Bindu no longer adjusts OS time from `bindu-root` or `bindu-node`.
Time synchronization must be handled by the host OS before installation.

Use one of these OS-level services:
- `systemd-timesyncd`
- `chronyd`
- `ntpd`

Recommended commands on Debian/Ubuntu:

```bash
sudo timedatectl set-ntp true
timedatectl status
```

Recommended commands on systems using chrony:

```bash
sudo systemctl enable --now chronyd
chronyc tracking
```

If your host uses classic NTP:

```bash
sudo systemctl enable --now ntpd
ntpq -p
```

Requirement:
- root and every node must have working OS time sync before joining the mesh
- root-side analytics, ordering, and correlation depend on correct host clocks

## 3) Preparing the Node Machine

### A) Ensure name resolution works

Name resolution is optional.
You only need network reachability to the root endpoints in `bootstrap.json`.
If you use DNS aliases in your environment, verify they resolve:

```
getent hosts bindu-dev   # Linux example
ping -c 1 bindu-dev
```

If you are in **local development only**, you may add `/etc/hosts` entries:

```
127.0.0.1 root
127.0.0.1 node-1
```

### B) Verify connectivity to root

From the node machine, ensure the root is reachable on the HTTPS signing endpoint.
The exact URL comes from `bootstrap.json` (`signing_url`).

## 4) Installing the Node

### A) Where `bindu-install-node` comes from

`bindu-install-node` is included in the node bundle generated by the root tooling.
Copy the bundle to the node machine and extract it.

### B) Run the installer

From inside the extracted bundle directory:

**Using Enrollment Token (Recommended for automation):**
```bash
sudo ./bindu-install-node --bundle . --token "<enrollment-token>" --install-service --service-auto-start
```

**Using Root Basic Auth:**
```bash
sudo ./bindu-install-node --bundle . --root-user <user> --root-pass <pass> --install-service --service-auto-start
```

Notes:

- `--bundle` points to the extracted node bundle directory.
- `--token` (or `--enrollment-token`) passes the single-use enrollment token scoped strictly to CSR signing.
- `--root-user` and `--root-pass` provide administrative Basic Auth credentials for root.
- `--install-service` registers a native Linux systemd unit (`bindu-node.service`).
- `--service-auto-start` enables and immediately starts the service upon installation.
- The installer automatically reads `signing_url` from `bootstrap.json` and contacts Root.

### E) What the installer does (high level)

- Scans bundle recursively to ensure **no private keys were leaked** into deployment packages.
- Tests TCP reachability to candidate parent addresses and writes `runtime/runtime-info/parent/` cache.
- Runs Preflight check against Root (`POST /api/v1/tls/preflight-node`) ensuring node is permitted in mesh topology and not currently in active conflict.
- Copies the node runtime into `releases/<version>/bindu-node` and sets up the supervisor launcher `bindu-node`.
- Generates a local 2048-bit RSA private key on the node machine.
- Sends a CSR to root for signing (via `signing_url`).
- Writes signed certificates (`runtime/tls/server.crt`) and private keys (`runtime/tls/server.key`, mode `0600`).
- Configures Linux systemd unit and supervisor restart marker (`runtime/restart.json`).

### F) Bootstrap & first contact

Each node bundle contains a `bootstrap.json` file.
It provides **first‑contact hints** (candidate parent addresses) and the **signing_url** used for enrollment.

## 5) TLS, Identity & Autonomous Lifecycle

- **node_id is the identity:** Certificates embed the logical `node_id` in the Subject CommonName and DNS Subject Alternative Names (SAN).
- **Enrolment Token Scoping:** First-contact signing uses `X-Enrollment-Token` via `POST /api/v1/tls/sign-node` (scoped strictly to certificate signing).
- **Preflight Conflict Prevention:** If the node is already actively running or not declared in the mesh topology, preflight immediately halts the install (`409 Conflict` or `403 Forbidden`).
- **Autonomous mTLS Renewal:** Active nodes autonomously monitor certificate expiration. When 30 days remain (or 80% of validity), the node calls `POST /api/v1/tls/renew-node` over mTLS to renew its certificate without downtime or manual operator actions.
- **Strict Directory Permissions:** The installer enforces POSIX `0700` on `runtime/tls`, `0600` on private keys, `0750`/`0640` on config and identity, and `0770`/`0660` on data and logs.
- **TLS Trust:** Uses internal CA trust from the bundle (no host OS trust store modifications required). Network IP changes do not require re-issuing certificates.

## 6) Resulting Files & Installed Binaries

### Installed Binaries

The Node installation is lightweight and spartan. Only the following binaries are deployed to the node machine:
*   **`bindu-node`** (top-level): The process supervisor launcher.
*   **`releases/<version>/bindu-node`**: The terminal runtime executable.
*   **`bindu-install-node`**: The self-contained node installer binary.

> [!IMPORTANT]
> **No `bindu-studio` on Nodes**:
> The `bindu-studio` CLI is an administrative/orchestration tool and is **not** included in the node deployment bundle or installed on node machines. It is only deployed on the Root or the operator's machine.
> 
> If you manually copy and install `bindu-studio` on a node or local development system, you can use the `bindu-studio node-service` commands (status, start, stop, restart) to manage the local `bindu-node` service, but this CLI will not be present on standard production nodes.

### Resulting Files (Canonical Split Layout)

After installation, files live under the canonical install prefix (`/opt/bindu/node` when running with sudo or `~/.bindu/node` for non-root users):

```text
<install>/
├── bindu-node                                # Launcher process supervisor
├── releases/
│   └── <version>/
│       ├── bindu-node                        # Release runtime executable
│       └── public/console/schema/            # Required message schemas
├── runtime/
│   ├── active.json                           # Active release pointer
│   ├── restart.json                          # Supervisor restart manager marker
│   ├── config/                               # Node runtime configuration
│   ├── identity/
│   │   └── node_identity.json                # Node logical identity (mode 0640)
│   ├── tls/
│   │   ├── ca.crt                            # Mesh Deployment CA Certificate
│   │   ├── server.crt                        # Signed Node Certificate (CN = node_id)
│   │   └── server.key                        # Local Private Key (mode 0600)
│   ├── runtime-info/
│   │   └── parent/
│   │       ├── last_parent.json              # Selected parent MQTT dial target
│   │       ├── parent_cache.json             # All candidate parent addresses
│   │       └── bootstrap.json                # Persisted parent seed address
│   ├── data/                                 # Local node storage & cache (mode 0770)
│   └── logs/                                 # Unified runtime logs (mode 0770)
└── bindu-install-node                        # Self-contained installer binary
```

Do **not** edit TLS files manually.
Do **not** add IP‑based certs or keys.

## 7) Verifying Success

### A) Logs

You should see log lines indicating:

- node identity is resolved
- TLS material created
- node is connecting

### B) Console view

Open the Bindu console on root and confirm the node appears in the mesh tree.

## 8) Common Errors & Fixes

### Error: signing endpoint unreachable

**Symptom:** Installer reports `root signing endpoint not reachable`.

**Fix:** Check that root is running and reachable on the HTTPS signing URL in `bootstrap.json`.

### Error: TLS mismatch

**Symptom:** TLS handshake failed, certificate mismatch.

**Fix:** Ensure the root HTTPS cert SANs include the address (or TLS name) used in `signing_url`.
Re‑run `bindu-install-node` after fixing root certs or bootstrap endpoint selection.

### Error: root unreachable

**Symptom:** Node cannot reach root ports.

**Fix:** Check firewall and port exposure. Confirm root is running.

### Error: node_id not found in mesh

**Symptom:** Installer rejects enrollment because node identity is not present in root mesh.

**Fix:** Add the node first with `bindu-studio mesh add`, apply with `bindu-studio mesh apply`, then rerun installer.

## 9) What Not To Do

- Do **not** regenerate certs manually.
- Do **not** use IP addresses as identities.
- Do **not** add hosts/IPs or URLs into `mesh.json`.
- Do **not** copy CA private keys to nodes.

---

If you follow this guide exactly, node installation is deterministic and repeatable.
